## 1. 为什么要重跑

2026-09-08 的 a1/a2/b1/b2 结果**不可用于评价 Macawiki**。

`scripts/install.py` 当时只支持 codex（`.agents/skills/macawiki`）与 claude
（`.claude/skills/macawiki`），而本实验的 agent 是 **codebuddy**，它只从
`~/.codebuddy/skills/` 或项目 `.codebuddy/skills/` 发现技能。B 组的 skill 被装进了
`.agents/skills/`，因此对 agent 完全不可见。

证据（解析 `runs/*/session-stream.jsonl` 的工具调用序列）：

| run | Skill 工具调用 | 含 macawiki 的命令 | session 日志中 "macawiki" 出现次数 |
|-----|---------------|-------------------|-----------------------------|
| a1  | 0 | 0 | 0 |
| a2  | 0 | 0 | 0 |
| b1  | 0 | 0 | 0 |
| b2  | 0 | 0 | 0 |

B 组从未调用过 Macawiki 一次，因此 `macawiki_queries: null` 的含义是「查了 0 次」，
不是「信号没采到」。a1/a2 与 b1/b2 的耗时差异测的是任务本身方差，不是 skill 收益。

修复：`scripts/install.py` 增加 `codebuddy` 目标（`.codebuddy/skills/macawiki`），
`run_porting_ab_eval.py` 的 B 组改用 `--agent codebuddy`，`install.sh` 改为对所有
受支持 agent 安装并加入 codebuddy 探测。

### skill 触发情况（本轮关键前提已满足）

| run | Skill 工具 | macawiki 命令 | 记录的 query 信号 |
|-----|-----------|--------------|-----------------|

| b4  | 1 | 3 | 2 |

b3 与 b4 均从 `.codebuddy/skills/macawiki` 调用了 `query.py`、`get_page.py`。
b3 的 `macawiki_queries` 为 null 是因为 agent 调用 `query.py` 时未带 `--signal-log`
（stream 中可见 3 条真实调用）→ **`macawiki_queries` 字段会系统性低估，不能作为
"是否用过 skill" 的判据**，应从 stream 的 `Skill` 工具调用次数取。

b4 的两次查询均有命中：`CUDAExtension cpp_extension cucc nvcc 扩展编译` → 4 条；
`mcPyTorch extension torch 自定义算子 构建` → 12 条。单次 elapsed 3.2–3.7ms。

### b4 的 timing 门失败原因

`benchmark/gather.py` 触发门控超时（默认 `--gate-timeout 3600`），非 agent 失败：
agent 自身 `returncode=0`，并在结束前已产出 scatter_segment 的完整计时。
b3 的 `gather.py` 正常完成并输出真实计时（SELECT/GAT/GAT_COO/GAT_CSR）。
判定为门控超时阈值不足 + 大矩阵（ldoor 323MB）耗时方差，不是移植质量问题。

## 3. 结论（待人工审查）

在**可比较**（同指纹、同 prompt、同模型、同门控）的三次完整 run 上：

- wall time：A 6374s / 6038s，B 5505s → B 低约 9–14%
- tokens_in：A 4.87M / 5.23M，B 4.39M → B 低约 10–16%
- turns：A 227 / 262，B 287 → B 更多但更短

方向一致指向「挂载 Macawiki 后更快、更省 token」，但 **n=2/组、方差大、b4 未跑完
gather**，且 b4 的 token 优势部分来自其提前结束。按 `docs/hardware-validation.md`，
本轮只能记 `recorded`，**不能得出 `verified` 结论**，也不能据此对外宣称加速比。
